# 全量缓存设计说明书

**子系统名称：** iam-auth-server — Secret 和 Policy 全量本地缓存

**文档版本：** V1.0

---

# 1. 背景与问题域

## 1.1 为什么需要全量缓存

iam-auth-server 作为数据面的鉴权决策服务，每个鉴权请求都需要查询 Secret（密钥）和 Policy（策略）数据。若每次鉴权都通过网络 gRPC 调用 iam-api-server，将引入以下问题：

- **延迟不稳定**：每次鉴权增加一次或多次网络 RTT
- **放大故障**：iam-api-server 的故障直接导致鉴权服务不可用
- **吞吐量受限**：鉴权 QPS 受限于上游 iam-api-server 的查询能力
- **成本浪费**：业务高峰期大量重复查询相同的数据

全量本地内存缓存的核心思路是：**将鉴权所需的全部元数据一次性加载到 iam-auth-server 本地内存中，鉴权时直接从本地读取，消除网络开销**。

## 1.2 资源特点分析

被缓存的两类资源（Secret 和 Policy）具有以下特征，这些特征直接决定了缓存策略的选择：

| 特征 | 描述 | 对设计的含义 |
|------|------|-------------|
| **大基数** | 全量缓存，系统中所有 Secret 和 Policy 都需加载 | 内存占用可预估，需关注存储效率 |
| **低频写** | 实际的写操作（创建/更新/吊销）频率远低于读操作 | 可以承受写操作带来的较大开销 |
| **频繁读** | 每次鉴权都需要读取相关数据 | 读路径必须极致优化，避免锁竞争和内存拷贝 |
| **弱一致性可容忍** | 缓存与数据库的不一致窗口极短（秒级），且业务可接受 | 放弃强一致模型，采用最终一致的异步刷新策略 |

## 1.3 设计目标

- **读性能最大化**：鉴权读路径不产生网络 IO 和磁盘 IO，不产生锁竞争
- **写代价隔离**：缓存更新的时间开销不影响正在进行的鉴权请求
- **最终一致性**：缓存与数据库的偏差控制在秒级
- **多实例一致性**：所有 iam-auth-server 实例的缓存最终收敛到相同状态

# 2. 总体架构

## 2.1 缓存在系统中的位置

全量缓存是 iam-auth-server 内部的本地模块，并非独立的中间件服务。它在整个 sup-iam 系统中的位置如下：

```
                          ┌──────────────────┐
                          │   iam-api-server  │
                          │   (控制面)         │
                          │   MySQL → 管理API  │
                          └────────┬─────────┘
                                   │ gRPC (全量查询)
                                   ▼
┌─────────────────────────────────────────────────────┐
│                 iam-auth-server (数据面)               │
│                                                      │
│  ┌──────────┐    ┌──────────────┐    ┌────────────┐ │
│  │          │    │              │    │            │ │
│  │ 鉴权请求   │───▶│   缓存读取    │◀───│   全量缓存   │ │
│  │ (API入口)  │    │  (服务层)     │    │ (本地内存)   │ │
│  │          │    │              │    │            │ │
│  └──────────┘    └──────────────┘    └──────┬─────┘ │
│                                             │       │
│                                   ┌─────────▼─────┐ │
│                                   │  缓存加载管理器  │ │
│                                   │  (LoadManager)  │ │
│                                   └────┬──────┬────┘ │
│                                        │      │      │
└────────────────────────────────────────┼──────┼──────┘
                                         │      │
                              ┌──────────▼──┐ ┌▼──────────┐
                              │  Redis       │ │  gRPC      │
                              │  Pub/Sub     │ │  全量拉取   │
                              │  (变更通知)   │ │  (初始加载) │
                              └─────────────┘ └───────────┘
```

## 2.2 核心设计思想

全量缓存的设计遵循 **"以写换读"** 原则：

- **读操作**：零网络 IO、零磁盘 IO、无锁读取
- **写操作**：承担所有开销，包括网络 IO（gRPC 全量拉取）、对象解析、缓存数据结构重建

这种权衡成立的前提是**低频写**——当写频率极低时，把复杂度集中到写路径是划算的。

# 3. 缓存数据组织

## 3.1 缓存实体

全量缓存维护两类独立的缓存池：

| 缓存池 | 键（Key） | 值（Value） | 说明 |
|--------|----------|------------|------|
| Secret 缓存 | AccessKey（字符串） | Secret 结构体 | 每个 Secret 包含 AccessKey、SecretKey、过期时间 |
| Policy 缓存 | SecretID（字符串） | Policy 列表 | 属于同一个 Secret 的所有 Policy 聚合为一个列表 |

### 3.1.1 Secret 缓存

以 AccessKey 为键，支持通过 AccessKey 直接查找到对应的 Secret 对象。每个鉴权请求的第一步是验证签名，这一步需要获取到 SecretKey，因此该缓存是鉴权流程的入口。

### 3.1.2 Policy 缓存

以 SecretID 为键，值是该 Secret 关联的 Policy 列表。同一个 Secret 下的所有 Policy 被聚合为组（group），一次查询即可获取全部策略。这种组织方式避免了 N+1 查询问题——如果每条 Policy 独立存储，查询一个 Secret 的策略时需要多次查找。

## 3.2 缓存容量考量

由于是全量缓存，内存占用量直接取决于 Secret 和 Policy 的总量。以典型部署场景为例：

- 假设 10,000 个 Secret，平均每个 Secret 绑定 50 条 Policy
- 每条 Secret 约 256 字节，每条 Policy 约 512 字节
- 总数据量 ≈ 10,000 × 256 + 500,000 × 512 ≈ 260 MB
- 加上 Ristretto 元数据开销（计数器和索引），总内存占用约在 500 MB 以内

# 4. 缓存加载机制

## 4.1 启动初始化

iam-auth-server 启动时，缓存模块执行一次全量数据加载：

```
iam-auth-server 启动
        │
        ▼
  初始化 gRPC 客户端 ───→ 连接 iam-api-server
        │
        ▼
  初始化本地缓存池 ───→ 创建 Secret 和 Policy 两个独立的 Ristretto 实例
        │
        ▼
  LoadManager.Start()
        │
        ├──▶ 全量拉取所有 Secret ──→ gRPC GetAllSecrets
        │       │                      │
        │       └──▶ 构建 Secret 缓存    │
        │                               │
        ├──▶ 全量拉取所有 Policy ────────┤
        │       │                      │
        │       └──▶ 构建 Policy 缓存    │
        │                               │
        └──▶ 启动后台协程 ──────────────┘
                ├── pubSubLoop()     ─── 订阅 Redis 变更通知
                ├── reloadQueueLoop() ── 缓存重新加载事件
                └── reloadLoop()     ─── 定时处理缓存刷新
```

**初始化流程的关键点**：

1. 先加载 Secret，再加载 Policy，顺序执行
2. 全量拉取使用 gRPC 流式或批量接口，一次性获取所有数据
3. 缓存构建完成后才对外暴露鉴权服务，保证启动期间不会读到空缓存

## 4.2 缓存构建过程

缓存构建是一个**离线构造、原子替换**的过程：

```
现有缓存 (旧)                   新缓存 (空)
    │                              │
    │                              ├── 从 gRPC 拉取全量数据
    │                              ├── 逐条写入新缓存实例
    │                              ├── 等待写入完成 (Wait)
    │                              │
    │                    原子替换 ──┼── Store(新缓存)
    │                              │
    ▼                              ▼
旧缓存被 GC 回收 ←──── 持有引用的请求继续使用
```

这种"先构建、再替换"的方式保证了：
- 构建过程中，旧缓存继续服务，不受影响
- 替换原子完成，不存在中间状态
- 持有旧缓存引用的请求仍能正常读取，完成后再被 GC 回收

# 5. 缓存更新机制

## 5.1 整体流程

缓存更新采用 **事件驱动 + 定时刷新的混合策略**：

```
iam-api-server (数据变更)
        │
        ├── 写入 MySQL
        ├── 发布变更通知到 Redis ──→ "iam.cluster.notification"
        │                                │
        ▼                                ▼
                              iam-auth-server 订阅 Redis
                                        │
                                        │ (pubSubLoop)
                                        ▼
                              解析通知类型 (PolicyChanged / SecretChanged)
                                        │
                                        │ (channel)
                                        ▼
                              reloadQueueLoop
                                        │
                                        │ (排队防抖)
                                        ▼
                              reloadLoop (定时 tick)
                                        │
                                        │ 到达 tick 且有排队事件
                                        ▼
                              全量重新拉取 → 原子替换缓存
```

## 5.2 变更通知通道

### 5.2.1 Redis Pub/Sub

- **通道名称**：`iam.cluster.notification`
- **消息序列化**：MessagePack 二进制格式
- **通知类型**：
  - `SecretChanged`：Secret 发生变更（创建、更新、吊销）
  - `PolicyChanged`：Policy 发生变更（创建、更新、删除）

### 5.2.2 变更通知的触发者

变更通知由 iam-api-server（控制面）在完成元数据写操作后发布。iam-auth-server 仅作为订阅者消费通知，不负责判断"是否需要刷新"——只要收到通知就触发重载检查，由 debounce 机制做聚合。

## 5.3 防抖（Debounce）机制

### 5.3.1 设计动机

在频繁变更的场景下（如批量导入策略），如果不做防抖，每次变更通知都触发一次全量重载，将产生严重的资源浪费。防抖机制的核心作用是：**将多个紧密相邻的变更通知合并为一次刷新**。

### 5.3.2 实现方式

防抖采用**两级缓冲**架构：

```
变更通知抵达
        │
        ▼
  第一级：无缓冲 channel
        │
        ├── Secret 变更 ──▶ secretChan ──▶ secretQueue (缓冲队列)
        │
        └── Policy 变更 ──▶ policyChan ──▶ policyQueue (缓冲队列)
                                             │
                                             ▼
  第二级：定时 tick (reloadTick)
        │
        ├── 检查 secretQueue 是否为空
        │     └── 非空 → 清空队列 → 执行全量重载
        │
        └── 检查 policyQueue 是否为空
              └── 非空 → 清空队列 → 执行全量重载
```

**关键设计决策**：

- Secret 和 Policy 的队列**独立**，各自的变更互不影响
- 同类型变更在 tick 间隔内只触发一次重载
- tick 间隔可配置（默认建议 1s），控制最大不一致窗口

### 5.3.3 时序示例

```
时间轴：
t0:  iam-api-server 修改 Secret-A → 发布 SecretChanged
t1:  iam-api-server 修改 Secret-B → 发布 SecretChanged
t2:  iam-api-server 修改 Secret-C → 发布 SecretChanged
t3:  reload tick 触发 → secretQueue 非空 → 执行一次全量重载
                          (三条变更被合并为一次重载)

结果：只用一次全量重载就同步了三次变更
```

## 5.4 刷新执行

当 reloadLoop 的 tick 到达且队列非空时，执行全量重载：

1. 通过 gRPC 调用 iam-api-server 的 `GetAllSecrets` 或 `GetAllPolicies` 接口
2. 构建全新的 Ristretto 缓存实例
3. 原子替换（Store），旧实例交 GC 回收

**刷新粒度**：整个缓存池（所有 Secret 或所有 Policy），而非增量更新。在全量数据量可控的前提下（百万级以内），全量重载的耗时在毫秒到秒级，可以接受。

# 6. 并发安全设计

## 6.1 临界资源

缓存的临界资源是两类缓存池的引用。读操作需要从缓存池中查找数据，写操作需要替换整个缓存池，两者可能并发执行。

## 6.2 保护策略

采用 **atomic.Value + 不可变替换** 策略：

```
┌─────────────────────────────────────────────┐
│              Cache 结构                       │
│                                              │
│  secrets: atomic.Value ──▶ *ristretto.Cache   │
│                                              │
│  policies: atomic.Value ──▶ *ristretto.Cache  │
│                                              │
│  读操作：Load() → Get(key)                      │
│  写操作：NewCache → Set数据 → Store(newCache)    │
└─────────────────────────────────────────────┘
```

### 6.2.1 读操作路径

```
请求到达 → secrets.Load() → *ristretto.Cache → Get(accessKey) → Secret 对象
```

- `atomic.Value.Load()` 是原子的，保证获取到的是完整的指针
- Ristretto 的 `Get` 是并发安全的，内部使用分片锁和无锁哈希
- 读路径不含任何显式锁

### 6.2.2 写操作路径

```
1. gRPC 拉取全量数据
2. ristretto.NewCache(config)      ← 创建新实例
3. 遍历数据，cache.Set(key, val)    ← 写入新实例
4. cache.Wait()                    ← 等待写入完成
5. secrets.Store(newCache)         ← 原子替换
                                    ← 旧缓存引用被 GC 回收
```

- 操作 1-4 完全独立于正在进行的读操作
- 操作 5 是原子的单条指令
- 旧缓存不会立即销毁，GC 会等待所有引用释放后回收

### 6.2.3 并发安全示意图

```
读协程 A                         写协程                           读协程 B
    │                              │                                │
    │   Load() → 旧缓存引用          │                                │
    │                              ├── 构建新缓存                    │
    │                              ├── Store(新缓存)                │
    │   Load() → 新缓存引用          │                                │
    │                              │                                │   Load() → 新缓存引用
    │                              │                                │
    │   继续使用旧缓存                │                                │
    │   直到函数返回                   │                                │
    │                              │                                │
    │   旧缓存 → 无引用 → GC 回收     │                                │
```

## 6.3 旧资源回收

旧缓存的回收完全由 Go GC 负责：

- 写操作 `Store()` 之后，旧缓存不再有全局引用
- 但正在进行的读操作可能仍持有旧缓存的引用
- Go GC 使用三色标记法，只有当旧缓存的所有引用都释放后，才会被回收
- 这种机制天然保证了不会出现读写冲突，且不需要引用计数

## 6.4 内存安全

由于旧缓存不会立即释放，如果缓存更新过于频繁，可能导致大量旧缓存同时存活，造成 OOM。为此需要以下保障：

- **限制更新速率**：通过 debounce 机制保证每秒最多一次重载
- **预估缓存大小**：单个缓存实例的内存占用应远小于可用内存
- **内存余量设计**：至少保证可以同时存活 2-3 个缓存实例

# 7. 多实例一致性

## 7.1 一致性模型

全量缓存提供 **最终一致性**：

- **不一致窗口**：从 iam-api-server 完成数据变更到所有 iam-auth-server 实例更新缓存，最长不超过 `reloadTick + 网络延迟`（通常 1-2 秒）
- **不同实例之间**：每个实例独立接收到变更通知，独立执行重载，无法保证同时完成
- **业务影响**：IAM 权限变更通常是审批驱动的（数分钟到数天），秒级不一致可以忽略

## 7.2 跨实例同步架构

```
iam-api-server
    │
    ├── 写入 MySQL
    └── 发布 Redis Pub/Sub ──────────────────────┐
                                                  │
                    ┌─────────────────────────────┼──────────────────────────┐
                    ▼                             ▼                          ▼
         ┌──────────────────┐          ┌──────────────────┐      ┌──────────────────┐
         │ iam-auth-server  │          │ iam-auth-server  │      │ iam-auth-server  │
         │ (实例 1)          │          │ (实例 2)          │      │ (实例 3)          │
         │                  │          │                  │      │                  │
         │ 订阅 Redis        │          │ 订阅 Redis        │      │ 订阅 Redis        │
         │ 收到通知 → 排入队列 │          │ 收到通知 → 排入队列 │      │ 收到通知 → 排入队列 │
         │ tick → 全量重载    │          │ tick → 全量重载    │      │ tick → 全量重载    │
         └──────────────────┘          └──────────────────┘      └──────────────────┘
```

关键点：
- 所有实例监听同一个 Redis 通道，收到相同的通知
- 每个实例独立决策何时重载（tick 相位可能不同）
- 不需要跨实例协调或分布式锁
- 新加入的实例通过启动时的全量加载自动获得最新数据

# 8. 容错与恢复

## 8.1 Redis 连接中断

| 场景 | 影响 | 恢复行为 |
|------|------|---------|
| Redis 短暂故障（< 10s） | 变更通知丢失 | 实例重连后继续监听，不会自动补发丢失的通知 |
| Redis 长时间故障 | 实例无法收到变更通知 | 缓存停留在旧版本直到 Redis 恢复 |

**设计取舍**：Redis 连接中断时，不触发兜底刷新。原因是：

1. 控制面（iam-api-server）不受影响，管理员仍可正常管理元数据
2. 数据面可以继续基于旧缓存提供鉴权服务，服务不降级
3. 缓存的不一致窗口随 Redis 故障时间延长，Redis 恢复后自动修复

若需要更强的保障，可增加额外策略（如定期无条件全量刷新），但会增加不必要的开销。

## 8.2 gRPC 拉取失败

当全量重载时 gRPC 调用失败：

- 记录错误日志
- 跳过本次重载
- 保留现有缓存继续服务
- 等待下一个 tick 重试

## 8.3 重载期间读请求

由于"先构建、后替换"的设计，重载过程对读请求完全透明：

- 重载进行中：读请求命中旧缓存
- 重载完成：后续读请求自动命中新缓存（原子替换）
- 重载失败：旧缓存保持不变，不影响任何请求

# 9. 缓存配置

## 9.1 缓存引擎参数

全量缓存底层使用 Ristretto（Dgraph 出品的高性能 Go 缓存库），以下是关键配置参数：

| 参数 | 说明 | 建议值 |
|------|------|--------|
| NumCounters | 准入/淘汰计数器的数量，决定追踪 key 访问频率的精度 | 期望 key 数量的 4 倍 |
| MaxCost | 缓存的最大开销（字节），达到上限后触发淘汰 | 预估数据量的 1.5 倍 |
| BufferItems | 异步操作的缓冲条目数 | 64 |

由于是全量缓存（不淘汰数据），实际使用中 MaxCost 应设置为大于所有数据的总开销，确保不会发生淘汰。

## 9.2 重载间隔

| 参数 | 默认值 | 说明 |
|------|--------|------|
| reloadTick | 1s | 防抖刷新 tick 间隔，控制不一致窗口 |

# 10. 与数据采集模块的关系

全量缓存和数据采集是 iam-auth-server 的两个独立模块，共享 Redis 基础设施但职责不同：

| 方面 | 全量缓存 | 数据采集（Analytics） |
|------|---------|---------------------|
| 数据流向 | iam-api-server → gRPC → 本地内存 | iam-auth-server → Redis → iam-pump → MongoDB |
| Redis 用途 | Pub/Sub 变更通知通道 | List 日志缓冲 |
| 数据特征 | Secret 和 Policy 元数据 | 鉴权决策日志 |
| 容错方式 | 旧缓存继续服务 | TTL 兜底防 OOM |

两者共享的 Redis 连接池已经做了隔离设计，不会相互影响。

# 11. 设计约束与局限

## 11.1 适用场景

- Secret 和 Policy 总量可控（百万级以内）
- 读频率远高于写频率
- 可以接受秒级不一致

## 11.2 不适用的场景

- **数据量极大**（千万级以上）：全量加载可能耗时过长，内存占用过高
- **写入频率高**（每秒数十次以上）：频繁全量重载将产生高额开销，此时需要增量更新方案
- **要求强一致性**：本设计只能保证最终一致性

## 11.3 当前版本未覆盖

- 缓存预热：新实例启动时全量加载已覆盖
- 缓存命中率监控：建议后续增加缓存命中/未命中指标暴露
- 增量更新：当数据量增长到一定程度后可作为优化方向
