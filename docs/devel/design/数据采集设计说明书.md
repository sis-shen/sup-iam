# 数据采集设计说明书

**子系统名称：** iam-pump（数据采集服务）

**文档版本：** V2.0

---

# 1. 概述

数据采集子系统负责将 iam-auth-server 产生的鉴权决策日志，从 Redis 缓冲层搬运到 MongoDB 等后端持久化存储中，供运维系统查询与分析。

整个数据采集体系分为**写侧**和**消费侧**两个子系统：

- **写侧（iam-auth-server）**：鉴权决策完成后，将决策日志异步写入 Redis，并设置 TTL 作为内存保护兜底
- **消费侧（iam-pump）**：从 Redis 消费授权日志，转存至 MongoDB 等后端存储

**核心设计目标：**
- 鉴权主流程与日志写入解耦，日志写入不阻塞鉴权
- 支持多种后端存储可插拔接入
- 多副本部署下保证数据不被重复消费
- Redis 内存安全保护，防止消费侧故障导致 Redis OOM

# 2. 数据流总体设计

## 2.1 系统上下文

```
┌──────────────┐     ┌────────────────┐     ┌──────────────┐
│ iam-auth-    │────>│     Redis      │<────│  iam-pump    │
│ server       │ 写入│  (授权日志缓冲)  │ 消费│  (数据采集)   │
│ (写侧)        │     │                │     │  (消费侧)     │
└──────────────┘     └────────────────┘     └──────┬───────┘
                                                    │
                                                    ▼
                                            ┌──────────────┐
                                            │   MongoDB    │
                                            │ (持久化日志)   │
                                            └──────┬───────┘
                                                    │
                                                    ▼
                                            ┌──────────────────┐
                                            │ iam-operating-   │
                                            │ system (运维系统) │
                                            └──────────────────┘
```

## 2.2 数据流转路径

```
写侧 (iam-auth-server)
  │
  ├── 鉴权决策完成
  ├── 构建日志记录 (含时间戳、用户、资源、决策结果等)
  ├── 送入异步缓冲通道 ── 不阻塞鉴权主流程
  │
  └── 批量写入协程 (由定时器或缓冲满触发)
        │
        ├── 二进制序列化 (MessagePack)
        ├── Pipeline RPUSH → Redis List
        └── TTL 兜底检查 → 无 TTL 则设置过期时间
              │
              ▼
        Redis List (analytics-iam-system-analytics)
              │
              ▼ LRANGE + DEL (原子消费)
              │
消费侧 (iam-pump)
  │
  ├── 定时器触发消费周期
  ├── 分布式锁争抢 (领导者选举)
  ├── 原子读取并删除 Redis 中的数据
  ├── 反序列化
  ├── 过滤器处理 (用户名黑白名单、省略详情)
  │
  └── 并发分发至所有已注册的 Pump 后端
        │
        ├── MongoDB Pump ── 分批写入 MongoDB
        └── (未来可扩展更多 Pump)
```

## 2.3 三大设计要点

数据采集系统围绕三个核心设计问题展开：

| 设计问题 | 解决方案 | 关键权衡 |
|----------|---------|---------|
| 如何不阻塞鉴权 | 异步缓冲通道 + 批量写入 | 可能丢失宕机前最后几秒的日志 |
| 如何防止重复消费 | 分布式锁 + 原子读取删除 | 锁故障时可能导致短时间重复 |
| 如何防止 Redis OOM | 写入侧 TTL 兜底 | 消费侧长时间宕机时会丢失过期数据 |

# 3. 写侧设计 — iam-auth-server

## 3.1 设计目标

写侧的核心设计目标是**异步非阻塞**。鉴权决策是数据面的核心路径，日志写入不能增加鉴权延迟。解决方案是：鉴权主流程只做"记录入队"，由后台协程负责实际写入。

- **异步非阻塞**：日志写入不能阻塞鉴权主流程
- **批量写入**：累积多条记录后批量写入 Redis，减少网络往返
- **内存保护兜底**：通过 Redis Key TTL 防止 pump 宕机时 Redis 内存被打爆

## 3.2 缓冲与写入策略

### 3.2.1 两级缓冲架构

写侧采用**通道缓冲 + 批量写入**的两级缓冲架构：

```
鉴权决策完成
      │
      ▼
┌──────────────────────────────┐
│  第一级：内存缓冲通道           │
│  容量可配置（默认约 1000 条）   │
│  作用：解耦鉴权主流程和 IO 流程  │
└──────────┬───────────────────┘
           │ 异步消费
           ▼
┌──────────────────────────────┐
│  第二级：批量写入缓冲区          │
│  条件：定时触发 OR 缓冲区满     │
│  作用：合并多条记录为一次网络 IO │
└──────────┬───────────────────┘
           │ Pipeline RPUSH
           ▼
        Redis List
```

**第一级缓冲（通道）**：鉴权完成后，日志记录被送入一个带缓冲的 Go channel。channel 的容量决定了鉴权主流程可以领先写入流程多少条记录。如果 channel 满，鉴权主流程会感受到背压（阻塞等待），但正常情况下不应发生。

**第二级缓冲（批量）**：后台协程从 channel 中消费记录，累积到缓冲区中。以下两个条件任一满足时触发实际写入：
- **定时触发**：距离上次写入超过配置的间隔（默认 10 秒）
- **缓冲区满**：累积的记录数量达到阈值

这种设计将多次小写入合并为一次大写入，显著减少 Redis 网络开销。

### 3.2.2 写入流程

```
┌───────────┐     ┌──────────────┐     ┌───────────┐
│ 鉴权主流程  │────>│ 缓冲通道      │────>│ 批量写入    │
│            │     │ (capacity N) │     │ 协程       │
│ RecordHit()│     │              │     │           │
└───────────┘     └──────────────┘     └─────┬─────┘
                                             │
                                    ┌────────▼────────┐
                                    │  Pipeline RPUSH  │
                                    │  + TTL 兜底检查   │
                                    └────────┬────────┘
                                             │
                                             ▼
                                       ┌──────────┐
                                       │  Redis   │
                                       │  List    │
                                       └──────────┘
```

## 3.3 序列化选择

写侧使用 **MessagePack** 二进制序列化格式，而非 JSON。选择 MessagePack 的原因：
- **更高的压缩率**：二进制格式比文本格式体积更小，减少 Redis 内存占用
- **更快的解析速度**：二进制序列化/反序列化的 CPU 开销低于 JSON
- **生态支持**：主流语言均有高效的 MessagePack 库支持

## 3.4 TTL 兜底策略

### 3.4.1 设计动机

TTL 兜底是写侧最核心的容错设计。当 iam-pump 消费侧宕机或网络分区时，Redis 中的日志会持续堆积。如果没有 TTL，Redis 内存会被日志打爆，影响 Redis 上的其他功能（如全量缓存的变更通知通道）。

### 3.4.2 工作原理

每次批量写入完成后，写入协程检查 Redis Key 的 TTL 状态：

```
批量写入完成
      │
      ├── 检查 Redis Key 的 TTL
      │     ├── 无 TTL → 设置 TTL (默认 24h)
      │     └── 已有 TTL → 不操作
      │
      └── 完成
```

关键点是：**只在 Key 没有 TTL 时才设置**，不会每次写入都重置 TTL。这意味着 TTL 是从第一次检查（或最近一次 Key 重建）开始倒计时，而非每次写入都刷新。

### 3.4.3 场景分析

| 场景 | TTL 行为 | 结果 |
|------|---------|------|
| pump 正常运行 | pump 每个周期 LRANGE+DEL 消费数据，Key 被删除 | TTL 自然失效，不影响正常流程 |
| pump 宕机/网络分区 | Redis 中日志持续堆积 | TTL 到期后自动淘汰，保护 Redis 内存 |
| pump 恢复上线 | 从 Redis 消费存量数据（TTL 未到期的部分） | 可能丢失 TTL 过期的那部分日志 |

### 3.4.4 为什么是写入侧负责 TTL？

TTL 兜底的策略是**在数据生产侧设置数据生命周期**，而非在消费侧：

- TTL 是最后一道防线，在 pump 不可用时才生效
- 由写入侧设定更合理——写入侧知道数据多久不消费就应丢弃
- 如果由 pump 设置 TTL，pump 宕机时没有任何机制能设置过期时间，兜底策略失效
- 数据生产方有能力控制数据在缓冲层中的生命周期

## 3.5 Redis Key 规范

| 项目 | 值 |
|------|-----|
| Key 前缀 | `analytics-` |
| Base Key | `iam-system-analytics` |
| 完整 Key | `analytics-iam-system-analytics` |
| 数据结构 | Redis List |
| 写入方式 | Pipeline RPUSH（批量） |
| 消费方式 | LRANGE + DEL（原子操作） |
| 兜底 TTL | 默认 24h |

# 4. 消费侧设计 — iam-pump

## 4.1 设计目标

消费侧的核心设计目标是**可靠搬运**——从 Redis 中读取日志数据，写入后端持久化存储，在此过程中保证数据不丢失、不重复、不错乱。

- **不丢失**：原子读取删除确保数据不会滞留在缓冲层
- **不重复**：分布式锁保证多副本下只有一个实例消费
- **可扩展**：插件化 Pump 架构支持多种后端存储

## 4.2 主循环架构

iam-pump 采用**定时轮询**的主循环架构：

```
启动
  │
  ├── 初始化日志、信号处理
  ├── 启动健康检查 HTTP 服务
  │
  └── 主循环 (定时器驱动)
        │
        ├── [每个周期]
        │   ├── 争抢分布式锁
        │   │   └── 失败 → 跳过本轮 (已有领导者在处理)
        │   │
        │   ├── 原子读取 + 删除 Redis 数据
        │   │
        │   ├── 反序列化 (MessagePack → 结构化记录)
        │   │
        │   ├── 应用过滤器
        │   │   ├── 省略详情字段 (按需)
        │   │   └── 用户名黑白名单过滤
        │   │
        │   └── 并发分发至所有 Pump
        │         ├── Pump A.WriteData()
        │         ├── Pump B.WriteData()
        │         └── ...
        │
        └── [收到停止信号] → 退出循环
```

### 4.2.1 为什么使用定时轮询而非事件驱动？

选择定时轮询而非 Redis 的 `BLPOP` 阻塞弹出，原因如下：

- **批量处理效率**：定时轮询可以一次拉取大量数据后批量写入，减少后端存储的写入次数
- **控制消费速率**：通过调整轮询间隔可精确控制消费频率
- **分布式锁兼容**：定时轮询与分布式锁的"定期争抢"模式天然契合
- **简单可靠**：轮询模型比事件驱动模型容错边界更清晰

### 4.2.2 消费周期设计

默认消费周期为 1 秒。这个间隔需要在延迟和开销之间平衡：

- **周期过短**：Redis 请求频率增加，但每次可能只取到少量数据，白白浪费网络开销
- **周期过长**：日志在 Redis 中停留时间延长，TTL 兜底可能触发，丢失数据的风险增大

1 秒的默认值在大多数场景下是合理的，日志量大时可适当缩短。

## 4.3 分布式互斥

### 4.3.1 设计动机

iam-pump 支持多副本部署以提高可用性。但如果多个实例同时从 Redis 消费同一份数据，会导致日志被重复写入 MongoDB。分布式互斥保证同一时间只有一个实例在处理数据。

### 4.3.2 领导者选举

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ iam-pump     │  │ iam-pump     │  │ iam-pump     │
│ 副本 1       │  │ 副本 2       │  │ 副本 3       │
│ (领导者)      │  │ (候选者)      │  │ (候选者)      │
│ 持有锁       │  │ 等待锁       │  │ 等待锁       │
└──────┬───────┘  └──────────────┘  └──────────────┘
       │
       │ 独占消费 Redis
       ▼
  ┌──────────┐
  │  Redis   │
  │ (锁 + 日志)│
  └──────────┘
```

使用 Redis 分布式锁（Redlock 算法）实现领导者选举：
- **锁 Key**：`iam-pump`
- **租约时长**：可配置（默认 10 分钟），防止领导者崩溃后锁长期不释放
- **行为**：未获取到锁的实例直接跳过当前周期，等待下一轮争抢

当领导者崩溃时，锁会在租约到期后自动释放，其他实例在下一个周期争抢到锁后成为新的领导者。

### 4.3.3 故障转移时序

```
t0:  实例 A 获取锁 → 成为领导者 → 开始消费
t1:  实例 A 崩溃
t2:  锁到期 (10分钟后，取决于租约配置)
t3:  实例 B 争抢到锁 → 成为新领导者 → 开始消费
     (此期间日志持续在 Redis 中堆积，TTL 兜底保护)
```

## 4.4 原子消费

消费侧从 Redis 读取数据时，需要保证**读取和删除是原子操作**，否则可能出现：

- 先读取后崩溃 → 数据既留在 Redis 中又被处理了部分 → 重复处理
- 先删除后崩溃 → 数据丢失

解决方案是使用 Redis 事务将 LRANGE（读取所有）和 DEL（删除 Key）打包为一个原子操作：

```
MULTI
LRANGE analytics-iam-system-analytics 0 -1    ← 读取所有日志
DEL analytics-iam-system-analytics              ← 删除 Key
EXEC
```

这个事务保证了：
- 要么全部执行成功（数据被可靠取出）
- 要么全部不执行（数据仍在 Redis 中，下个周期重试）
- 不存在"读了一半"或"删了一半"的中间状态

## 4.5 过滤机制

在将日志写入后端存储前，iam-pump 提供两级过滤：

### 4.5.1 详情省略

鉴权日志中可能包含策略匹配详情（Reason 字段），这些信息在运维分析时可能不需要。通过 `omit_detail_recoding` 配置可以在写入存储前清空该字段，减少存储开销。

省略配置分两层级：
- **全局级别**：对所有 Pump 生效
- **Pump 级别**：只对特定 Pump 生效，可覆盖全局配置

### 4.5.2 用户名过滤

支持按用户名进行黑白名单过滤：
- **白名单模式**：只采集指定用户的日志
- **黑名单模式**：跳过指定用户的日志
- **黑名单优先级高于白名单**

过滤在写入 Pump 前统一应用，避免敏感用户的日志写入后端存储。

# 5. Pump 插件架构

## 5.1 设计模式

Pump 插件架构采用**策略模式 + 原型模式**：

- **策略模式**：所有 Pump 实现同一接口，iam-pump 主循环可以统一对待
- **原型模式**：每个 Pump 类型注册一个原型实例，通过 `New()` 方法克隆出新实例

```
                   ┌──────────────────┐
                   │   PumpInterface   │
                   │  (策略接口)        │
                   └────────┬─────────┘
                            │ 实现
              ┌─────────────┼──────────────┐
              ▼             ▼              ▼
      ┌────────────┐ ┌────────────┐ ┌────────────┐
      │ MongoPump  │ │  KafkaPump │ │  其他 Pump  │
      │  (当前内置) │ │  (未来扩展) │ │  (未来扩展)  │
      └────────────┘ └────────────┘ └────────────┘
              │
      ┌───────┴────────┐
      │ 原型注册表       │
      │ "mongo" → 原型  │
      └────────────────┘
```

**Pump 的生命周期：**
1. **注册**：Pump 类型在启动时注册到原型注册表
2. **实例化**：根据配置，从原型克隆出带独立配置的实例
3. **初始化**：配置 Pump 的过滤器、超时、后端连接参数
4. **写入**：主循环调用 `WriteData()` 将日志写入后端
5. **未涉及销毁**：当前版本未实现 Pump 的动态销毁

## 5.2 Pump 契约

每个 Pump 需要满足以下契约：

| 能力 | 说明 |
|------|------|
| 名称标识 | 返回 Pump 的唯一名称，用于配置路由 |
| 原型克隆 | 返回一个新的独立实例，每个实例有自己的状态 |
| 初始化 | 接收配置，建立后端连接 |
| 数据写入 | 接收一批日志记录，写入后端存储 |
| 超时控制 | 单次写入有超时限制，超时后放弃本次写入 |
| 过滤能力 | 可配置用户名黑/白名单和详情省略 |
| 线程安全 | 多个 Pump 实例并发写入时互不影响 |

## 5.3 当前内置 Pump：MongoDB

当前版本内置一个 MongoDB Pump 实现：

### 5.3.1 写入策略

MongoDB Pump 采用**大小感知分批写入**策略：

```
从主循环接收一批记录
      │
      ├── 遍历记录，估算每条记录的字节大小
      ├── 累积到当前批次
      │
      ├── 当批次大小超过阈值 → 写入 MongoDB
      │                           │
      │                           └── 启动协程并发写入
      │
      └── 处理完所有记录 → 写入最后一批
```

- 基于字节大小分片，而非基于记录条数
- 过大的单条记录会被裁减（省略详情字段）
- 分批写入可并发进行，提高吞吐量

### 5.3.2 存储容量控制

MongoDB Pump 支持 Capped Collection（固定大小集合）：
- 可配置最大存储空间（默认 5GB）
- 当集合达到上限时，自动淘汰最旧的数据
- 写入量可控时也可以关闭此功能，使用普通集合

### 5.3.3 连接安全

- 支持标准 MongoDB URI 连接
- 支持 SSL/TLS 加密传输（含 CA 证书验证和双向证书认证）
- 连接中断时自动重试（5 秒间隔）
- 兼容 AWS DocumentDB

## 5.4 Pump 写入保障

- **独立协程**：每个 Pump 在独立的 goroutine 中写入，一个 Pump 的故障不影响其他 Pump
- **超时控制**：每个 Pump 有独立的写入超时，超时后记录告警但不阻塞主循环
- **慢写入告警**：如果某个 Pump 写入耗时超过消费周期，发出告警日志

# 6. 部署架构

## 6.1 多副本部署拓扑

iam-auth-server 与 iam-pump 均支持多副本部署，与 Redis 和 MongoDB 在同一可信网络内：

```
                    ┌──────────────────┐
                    │   LoadBalance    │
                    └────────┬─────────┘
```

**关键部署原则：**

| 组件 | 部署方式 | 说明 |
|------|---------|------|
| iam-auth-server | 多副本，水平扩展 | 每个实例独立写入 Redis，无需协调 |
| iam-pump | 多副本，主备切换 | 通过分布式锁保证同一时间只有一个实例消费 |
| Redis | 单节点或集群 | 作为日志缓冲层，承受高频写入 |
| MongoDB | 副本集或分片集群 | 日志持久化存储，由运维系统查询 |

## 6.2 配置要点

### 6.2.1 写侧（iam-auth-server）

| 配置项 | 作用 | 调优建议 |
|--------|------|---------|
| 缓冲通道容量 | 控制鉴权主流程领先写入的日志条数 | QPS 高时适当增大 |
| 刷新间隔 | 控制日志写入 Redis 的最大延迟 | 对延迟敏感时缩短 |
| TTL 兜底时长 | 控制日志在 Redis 中的最大存活时间 | 与 pump 恢复时间匹配 |
| 详情记录开关 | 是否记录策略匹配详情 | 存储空间紧张时关闭 |

### 6.2.2 消费侧（iam-pump）

| 配置项 | 作用 | 调优建议 |
|--------|------|---------|
| 消费周期 | 控制从 Redis 拉取数据的频率 | 日志量大时缩短 |
| 锁租约时长 | 分布式锁的持有时间 | 多副本部署时需一致 |
| Capped Collection | 控制 MongoDB 最大存储空间 | 建议启用，防日志无限增长 |

## 6.3 优雅关停

iam-pump 支持优雅关停：

1. 收到停止信号（SIGINT/SIGTERM）后，主循环退出 select
2. 正在进行的 Pump 写入允许完成
3. 如果再次收到停止信号，强制退出

这保证了关停过程中不会丢失已经读取到内存中的数据。

# 8. 安全注意事项

- 鉴权日志中不应包含 Secret Key（SK）等敏感信息，该约束由上游保证
- 策略匹配详情（Reason 字段）可通过配置在写入存储前清空，避免敏感策略信息泄露
- iam-pump 仅部署在可信内网，不对公网暴露端口
- TTL 是防止 Redis 内存被打爆的最后一道防线，建议始终启用

---

# 9. 设计约束与局限

## 9.1 适用场景

- 日志量可控，Redis 作为缓冲层可以容纳消费侧短期宕机期间的积压
- 可以接受秒级的日志采集延迟
- 需要插件化的后端存储支持

## 9.2 不适用的场景

- **需要实时日志分析**：本系统的延迟在秒级，不适合实时性要求高的场景
- **日志量极大导致 TTL 频繁触发**：此时需要增大 TTL 或引入更强大的缓冲层（如 Kafka）
- **要求精确一次语义**：当前架构只能保证至少一次，极端故障下可能重复

## 9.3 当前版本未覆盖

- Pump 的动态注册与销毁（当前为启动时静态注册）
- 日志的索引和全文搜索（由下游系统负责）
- 更丰富的过滤规则（如按资源、按操作类型过滤）
